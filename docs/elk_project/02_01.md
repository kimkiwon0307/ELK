
# ELK 프로젝트 학습

## 2장 1교시. Elasticsearch 기본 구조 및 서버 구축

### 1. Elasticsearch란?

Elasticsearch는 데이터를 색인(Indexing), 저장, 검색 및 분석하는 분산 검색 엔진이다.

**주요 역할**
- 로그 데이터 저장
- 필요한 로그 검색
- 대량의 데이터 분석
- Kibana에 검색 결과 제공

---

### 2. Elasticsearch 핵심 개념

| 개념 | 설명 |
|---|---|
| Node | 실행 중인 Elasticsearch 인스턴스 하나 |
| Cluster | 하나 이상의 Node로 구성된 집합 |
| Index | 관련 Document를 관리하는 논리적 단위 |
| Document | JSON 형식의 데이터 한 건 |
| Field | Document 내부의 개별 항목 |
| Shard | 인덱스 데이터를 나누어 저장·처리하는 단위 |
| Replica | Primary Shard의 복제본 |

**중요**
- Node 1개로도 Cluster를 구성할 수 있다.
- 하나의 Index는 여러 Shard로 나눌 수 있다.
- Replica는 장애 발생 시 가용성을 높이는 데 사용한다.
- 단일 노드에서는 같은 Primary의 Replica를 해당 노드에 함께 배치할 수 없다.

Document 예시:

```json
{
  "level": "ERROR",
  "service": "spring-app",
  "message": "Database connection failed"
}
```

- Document: JSON 전체
- Field: level, service, message
- Index: 이러한 Document들을 모아 관리하는 단위

### 4. 주요 설치 및 점검 명령어

#### 서버 자원 점검

```bash
# OS 확인
cat /etc/os-release

# 메모리 확인
free -h

# 디스크 확인
df -h

# IP 주소 확인
ip -br addr

# 라우팅 정보 확인
ip route
```

설치 전에 서버 자원과 네트워크 상태를 점검하여 이후 장애 발생 시 원인을 구분하기 쉽게 한다.

#### Docker 점검

```bash
# Docker 서비스 확인
sudo systemctl status docker

# Docker 컨테이너 확인
sudo docker ps

# 모든 컨테이너 확인
sudo docker ps -a

# 컨테이너 로그 확인
sudo docker logs --tail 50 es01
```

#### Elasticsearch 커널 설정

```bash
# 현재 메모리 매핑 한도 확인
sysctl vm.max_map_count

# Elasticsearch 권장 설정 적용
echo 'vm.max_map_count=1048576' | \
sudo tee /etc/sysctl.d/99-elasticsearch.conf

sudo sysctl --system
```

**vm.max_map_count란?**

프로세스가 사용할 수 있는 메모리 매핑 영역 수의 상한을 제어하는 리눅스 커널 설정이다.

Elasticsearch 실행을 위해 적절한 값으로 설정해야 한다.

#### Docker 네트워크 및 Volume

```bash
# Docker 네트워크 생성
sudo docker network create elastic

# Docker Volume 확인
sudo docker volume ls
```

Docker Volume은 컨테이너가 삭제되거나 재생성되어도 데이터를 별도로 유지하기 위해 사용한다.

단, Volume 자체를 삭제하거나 디스크 장애가 발생하면 데이터가 사라질 수 있으므로 별도 백업이 필요하다.

### 5. Elasticsearch 설치 후 정상 동작 검증

**핵심: 컨테이너 실행 확인 → API 응답 확인 → Cluster Health 확인**

#### ① Docker 컨테이너 상태 확인

```bash
sudo docker ps
```

확인 사항:
- es01 컨테이너 존재 여부
- STATUS가 Up인지 확인

**주의:** Up이라고 해서 Elasticsearch가 정상적으로 API 요청을 처리한다는 뜻은 아니다.

#### ② Elasticsearch API 확인

```bash
curl --cacert ./http_ca.crt \
  -u elastic \
  https://localhost:9200
```

확인 사항:
- 인증 성공 여부
- Elasticsearch 정보가 JSON으로 반환되는지
- 서버가 HTTP API 요청에 정상 응답하는지

#### ③ Cluster Health 확인

```bash
curl --cacert ./http_ca.crt \
  -u elastic \
  'https://localhost:9200/_cluster/health?pretty'
```

확인 사항:
- 클러스터 상태
- 노드 개수
- Primary Shard 상태
- 할당되지 않은 Shard 개수

**Cluster Health 상태**

| 상태 | 의미 |
|---|---|
| green | 모든 Primary 및 Replica Shard가 할당됨 |
| yellow | Primary는 할당되었지만 일부 Replica가 미할당됨 |
| red | 일부 Primary Shard가 미할당됨 |

단일 노드 환경에서 Replica가 존재하면 yellow가 발생할 수 있다.

**중요한 구분**
- docker ps = 컨테이너 프로세스 실행 확인
- curl API = Elasticsearch 서비스 응답 확인
- Cluster Health = 노드 및 샤드 할당 상태 확인

위 세 가지는 좋은 기본 검증 절차이지만 모든 장애에서 절대적으로 고정된 순서는 아니다.

### 7. 추가 질문 ② Elasticsearch에서 인증서를 사용하는 이유

Elasticsearch는 HTTPS(TLS) 통신을 통해 데이터를 보호할 수 있다.

**인증서를 사용하는 주요 목적**

1. 접속 대상 서버의 신원을 검증한다.
2. 신뢰할 수 있는 서버와 암호화된 TLS 연결을 설정한다.
3. 통신 중 데이터 노출 및 변조 위험을 줄인다.

#### HTTP와 HTTPS의 차이

| 구분 | HTTP | HTTPS |
|---|---|---|
| 통신 암호화 | 없음 | TLS 암호화 |
| 데이터 보호 | 평문 노출 위험 | 기밀성·무결성 보호 |
| 서버 인증서 검증 | 없음 | 인증서 검증 가능 |

#### http_ca.crt란?

`http_ca.crt`는 Elasticsearch 서버의 인증서가 신뢰할 수 있는 CA에 의해 발급되었는지 검증하기 위한 CA 인증서이다.

Elasticsearch는 보안 자동 구성 시 자체 CA와 서버 인증서를 생성할 수 있다.

클라이언트는 자체 CA를 기본적으로 신뢰하지 않을 수 있으므로 CA 인증서를 지정하여 검증한다.

#### curl 인증서 사용 예시

```bash
curl --cacert ./http_ca.crt \
  -u elastic \
  https://localhost:9200
```

| 명령어 | 의미 |
|---|---|
| curl | HTTP 요청 전송 |
| --cacert | 신뢰할 CA 인증서 지정 |
| ./http_ca.crt | CA 인증서 파일 |
| -u elastic | elastic 사용자 인증 |
| https:// | TLS 암호화 통신 |
| localhost:9200 | Elasticsearch API 주소 |

**반드시 구분하기**

- HTTPS(TLS) = 통신 암호화 및 무결성 보호
- http_ca.crt = 서버 인증서의 신뢰성 검증
- elastic 사용자/비밀번호 = 사용자 인증

인증서 검증과 사용자 인증은 서로 다른 과정이다.

#### 인증서 관련 오류

CA 인증서를 신뢰하지 못하는 경우:

```text
SSL certificate problem:
unable to get local issuer certificate
```

이 오류는 서버 인증서의 신뢰성을 검증하지 못했다는 의미다.

올바른 CA 인증서, 파일 경로, 서버 주소 등을 확인해야 한다.

`curl -k`는 인증서 검증을 생략하므로 일반적인 해결 방법으로 사용하지 않는다.

### 8. Elasticsearch 장애 점검

| 장애 증상 | 점검 내용 |
|---|---|
| 컨테이너 실행 실패 | docker ps -a, docker logs |
| API 연결 실패 | 9200 포트, 컨테이너 상태 |
| 401 Unauthorized | 사용자 이름 및 비밀번호 |
| 인증서 오류 | CA 인증서 및 HTTPS 설정 |
| 메모리 부족 | VM 메모리와 컨테이너 제한 |
| Cluster yellow | Replica Shard 할당 상태 |
| Cluster red | Primary Shard 미할당 원인 |
| 메모리 매핑 오류 | vm.max_map_count |

**장애 대응 기본 원칙**

1. 현재 상태 확인
2. 오류 로그 확인
3. 원인에 대한 가설 수립
4. 설정 또는 장애 원인 수정
5. 동일한 방법으로 정상 복구 검증

오류가 발생했다고 무조건 재설치하거나 재부팅하지 않는다.

### 9. 확인문제 및 정답

**Q1. Elasticsearch에서 Node란?**

정답: 실행 중인 Elasticsearch 인스턴스 하나

**Q2. Cluster는 반드시 여러 Node가 필요한가?**

정답: 아니다. Node 하나로도 Cluster를 구성할 수 있다.

**Q3. Elasticsearch의 기본 HTTP API 포트는?**

정답: 9200

**Q4. Docker Volume이 필요한 이유는?**

정답: 컨테이너 재생성 시에도 저장 데이터를 유지하기 위해서이다.

**Q5. docker ps에서 Up이면 서비스가 정상인가?**

정답: 아니다. API 응답과 Cluster Health까지 추가 확인해야 한다.

**Q6. Elasticsearch가 정상적으로 작동하는지 검증하는 방법은?**

정답:
1. docker ps로 컨테이너 실행 상태 확인
2. curl로 Elasticsearch API 응답 확인
3. Cluster Health API로 노드와 샤드 상태 확인
4. 문제가 있다면 docker logs로 오류 분석

#### 추가 확인문제

**Q7. curl을 사용하는 이유는?**

정답: Elasticsearch HTTP API에 실제 요청을 보내 서비스가 정상 응답하는지 확인하기 위해서이다.

**Q8. Elasticsearch 인증서를 사용하는 이유는?**

정답: TLS 통신에서 서버 신원을 검증하고 암호화된 통신을 안전하게 수립하기 위해서이다.

**Q9. --cacert와 -u의 차이는?**

정답:
- --cacert: 서버 인증서를 검증할 CA 지정
- -u: Elasticsearch 사용자 인증 정보 전달

### 10. 면접 대비 핵심 답변

**Q. Elasticsearch 설치 후 정상 동작 여부를 어떻게 검증하셨나요?**

A. 먼저 Docker 컨테이너가 실행 중인지 확인했습니다. 이후 curl을 이용해 Elasticsearch API 응답을 확인하고, Cluster Health API를 통해 노드와 샤드 할당 상태를 점검했습니다. 오류가 발생하면 컨테이너 로그를 통해 원인을 확인하도록 했습니다.

**Q. Elasticsearch에서 HTTPS 인증서를 사용하는 이유는 무엇인가요?**

A. 서버 신원을 검증하고 TLS를 통해 통신 내용을 암호화하기 위해서입니다. 자체 CA 인증서를 사용하는 환경에서는 curl의 --cacert 옵션으로 해당 CA를 지정하여 서버 인증서를 검증합니다.

### 11. 최종 핵심 암기

- Node = Elasticsearch 인스턴스 하나
- Cluster = 하나 이상의 Node 집합
- Index = 관련 Document를 관리하는 단위
- Document = JSON 데이터 한 건
- Shard = 인덱스를 나눈 데이터 저장·처리 단위
- 9200 = Elasticsearch HTTP API
- Docker Volume = 데이터 영속성
- docker ps = 컨테이너 실행 상태
- curl = 실제 API 동작 검증
- Cluster Health = 클러스터 및 샤드 할당 상태
- docker logs = 장애 원인 분석
- HTTPS = TLS 암호화 통신
- http_ca.crt = 서버 인증서 신뢰성 검증
- -u elastic = 사용자 인증

**가장 중요한 원칙**

"설치했다"와 "정상적으로 동작한다"는 다르다.

서비스를 설치한 후에는 실제 요청을 보내 정상적으로 작동하는지 검증해야 한다.

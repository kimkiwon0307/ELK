
# ELK 프로젝트 학습

## 1장 2교시. 로그 수집·가공·저장·검색의 동작 원리

### 1. 전체 로그 처리 흐름

**로그 수집 및 저장**

Spring Boot → Filebeat → Logstash → Elasticsearch

**로그 조회 및 검색**

Kibana → Elasticsearch → Kibana

| 기술 | 주요 역할 |
|---|---|
| Spring Boot | 애플리케이션 로그 생성 |
| Filebeat | 로그 파일 수집 및 전송 |
| Logstash | 로그 수신·가공·전달 |
| Elasticsearch | 로그 색인·저장·검색 |
| Kibana | 로그 조회·시각화 |

**핵심:** Kibana는 로그를 직접 저장하지 않고 Elasticsearch에 검색을 요청한다.

---

### 2. Filebeat 동작 원리

Filebeat는 서버의 로그 파일을 읽어 Logstash 또는 Elasticsearch로 전송하는 수집 도구이다.

**주요 구성요소**

| 구성요소 | 역할 |
|---|---|
| Input | 수집할 로그 파일을 탐색하고 관리 |
| Harvester | 실제 로그 파일을 읽음 |
| Registry | 파일별 수집 상태와 읽은 위치 등을 기록 |

**동작 과정**

1. Input이 수집 대상 파일을 발견한다.
2. Harvester가 로그 파일을 읽는다.
3. 읽은 로그를 출력 대상으로 전송한다.
4. Registry에 수집 상태를 기록해 재시작 시 활용한다.

**Registry가 필요한 이유**

Filebeat가 재시작되더라도 기존 파일의 수집 상태를 참고해 이어서 처리하기 위해서이다.

단, Registry가 로그 중복이나 유실을 모든 상황에서 완전히 방지하는 것은 아니다.

**핵심 암기**
- Harvester = 실제 파일 읽기
- Registry = 수집 상태 기억

---

### 3. Logstash 동작 원리

Logstash는 로그를 수신하고 필요한 형태로 가공해 Elasticsearch 등에 전달하는 도구이다.

**세 가지 처리 단계**

| 단계 | 역할 |
|---|---|
| Input | 데이터 수신 |
| Filter | 데이터 분석 및 가공 |
| Output | 처리한 데이터 전달 |

**동작 과정**

Input → Filter → Output

Filter는 필요한 경우에 사용하며, 로그를 가공하지 않고 전달할 수도 있다.

**가공 전 로그**

```text
2026-10-27 10:00:10 ERROR [req-002] Database connection failed
```

**가공 후 JSON 예시**

```json
{
  "@timestamp": "2026-10-27T10:00:10+09:00",
  "level": "ERROR",
  "requestId": "req-002",
  "message": "Database connection failed"
}
```

로그를 구조화하면 레벨, 시간, 요청 ID 등을 조건으로 검색하기 편리해진다.

대표적인 Filter:
- grok: 로그 문자열에서 패턴을 이용해 필드 추출
- date: 로그의 시간 문자열을 날짜·시간으로 변환
- mutate: 필드 추가·수정·삭제 등

**핵심 암기**
- Input = 입력
- Filter = 가공
- Output = 출력

---

### 4. Elasticsearch 동작 원리

Elasticsearch는 데이터를 색인하고 저장하여 다양한 조건으로 검색할 수 있도록 한다.

**색인(Indexing)이란?**

데이터를 검색에 적합한 구조로 처리하는 작업이다.

**주요 용어**

| 용어 | 역할 |
|---|---|
| Index | 관련 문서를 관리하는 논리적 단위 |
| Document | JSON 형태의 데이터 한 건 |
| Field | Document 안의 개별 항목 |
| Mapping | Field의 데이터 타입 정의 |

**Document 예시**

```json
{
  "level": "ERROR",
  "requestId": "req-002",
  "message": "Database connection failed",
  "status": 500
}
```

위 JSON 전체가 Document 한 건이다.

level, requestId, message, status는 각각 Field이다.

**핵심**
- Index = 문서들을 관리하는 단위
- Document = 데이터 한 건
- Field = 데이터의 개별 항목
- Mapping = 필드 타입 규칙

---

### 5. Kibana 동작 원리

Kibana는 Elasticsearch에 저장된 데이터를 검색하고 시각화하는 웹 인터페이스이다.

**동작 과정**

1. 운영자가 Kibana에 검색 조건을 입력한다.
2. Kibana가 Elasticsearch에 검색을 요청한다.
3. Elasticsearch가 조건에 맞는 문서를 반환한다.
4. Kibana가 검색 결과를 화면에 표시한다.

**KQL 검색 예시**

```text
level: "ERROR"
```

로그가 검색되지 않는다고 반드시 데이터가 유실된 것은 아니다.

Data View, 시간 범위, 검색 조건 등을 먼저 확인해야 한다.

### 6. 리눅스 실습 명령어

#### 6-1. 로그 파일 확인

```bash
cd ~/elk-project/ch01

cat app.log
wc -l app.log
```

- cat: 파일 내용 출력
- wc -l: 줄바꿈 기준 줄 수 확인

#### 6-2. 새로운 로그 감지

터미널 A:

```bash
tail -n 0 -F app.log
```

터미널 B:

```bash
printf '%s\n' '2026-10-27 10:00:12 ERROR [req-002] HTTP 500' >> app.log
```

옵션 설명:

| 옵션 | 의미 |
|---|---|
| -n 0 | 기존 내용은 출력하지 않음 |
| -F | 파일 이름 기준으로 변경 사항을 계속 추적 |
| >> | 파일 끝에 내용 추가 |

**목적**

로그 파일에 새로운 데이터가 추가되면 수집 도구가 이를 감지한다는 개념을 이해한다.

※ tail은 Filebeat 자체가 아니며 실제 Registry와 전송 기능은 구현하지 않는다.

#### 6-3. 로그 필드 추출

```bash
awk '$3=="ERROR" {print "시간="$2, "레벨="$3, "요청ID="$4}' app.log
```

- awk: 텍스트 필드 처리
- $2: 두 번째 필드(시간)
- $3: 세 번째 필드(로그 레벨)
- $4: 네 번째 필드(요청 ID)

공백으로 구분된 이번 실습 로그에 적용되는 예시이다.

**목적**

문자열 로그에서 필요한 필드를 추출하는 Logstash 가공 원리를 체험한다.

#### 6-4. 로그 검색 및 검증

```bash
grep -c "ERROR" app.log

grep "req-002" app.log

wc -l app.log
```

수업에서 사용한 로그 파일 기준 예상 결과:

| 항목 | 예상 결과 |
|---|---|
| ERROR 포함 줄 | 2줄 |
| req-002 포함 줄 | 3줄 |
| 전체 로그 | 4줄 |

위 결과는 리눅스 실습의 검증 기준이며 실제 ELK 구축 성공을 의미하지는 않는다.

### 7. 장애 대응 기본 원리

**상황: Spring Boot에서 ERROR가 발생했는데 Kibana에서 로그를 검색할 수 없다.**

단계별 확인:

1. Spring Boot
   - 오류 로그가 실제 생성되었는지 확인한다.

2. Filebeat
   - 로그 파일 경로와 수집 상태를 확인한다.
   - Logstash로 전송되는지 확인한다.

3. Logstash
   - 로그가 수신되는지 확인한다.
   - Filter 오류와 Output 설정을 점검한다.

4. Elasticsearch
   - 인덱스와 문서가 존재하는지 확인한다.
   - 저장 및 검색이 정상인지 점검한다.

5. Kibana
   - Data View를 확인한다.
   - 검색 시간 범위와 조건을 점검한다.

**장애 대응 원칙**

로그 생성 → 수집 → 가공 → 저장 → 검색

전체 흐름에서 어느 단계가 실패했는지 순서대로 원인을 좁힌다.

### 8. 확인문제 핵심 복습

**Q1. Filebeat의 Harvester는 무엇인가?**

정답: 로그 파일을 실제로 읽는 구성요소이다.

**Q2. Filebeat Registry는 왜 필요한가?**

정답: 파일별 수집 상태와 읽은 위치 등을 기억하여 재시작 이후에도 활용하기 위해서이다.

**Q3. Logstash의 Filter는 무엇을 하는가?**

정답: 로그 문자열을 분석하고 필요한 필드를 추출하거나 수정한다.

**Q4. Elasticsearch의 Document는 무엇인가?**

정답: Elasticsearch에 저장되는 JSON 형태의 데이터 한 건이다.

**Q5. Elasticsearch에는 로그가 있는데 Kibana에서 검색되지 않는다면?**

정답: Kibana의 Data View, 시간 범위, 검색 조건 등을 확인한다.

**Q6. Harvester와 Registry의 차이는?**

정답:
- Harvester는 실제 로그 파일을 읽는다.
- Registry는 파일의 수집 상태를 기억한다.

**Q7. Kibana에서 ERROR 로그가 보이지 않을 때 점검 순서는?**

모범답안:

Spring Boot에서 로그 생성 여부를 확인하고, Filebeat 수집 및 전송 상태를 점검한다.

이후 Logstash의 수신·가공 상태와 Elasticsearch의 저장 상태를 확인한다.

Elasticsearch에 로그가 정상 저장되어 있다면 Kibana의 Data View와 시간 범위 및 검색 조건을 점검한다.

### 9. 반드시 암기할 것

**Filebeat**
- Input = 수집 대상 관리
- Harvester = 실제 파일 읽기
- Registry = 수집 상태 기억

**Logstash**
- Input = 수신
- Filter = 가공
- Output = 전달

**Elasticsearch**
- Index = 문서 관리 단위
- Document = JSON 데이터 한 건
- Field = 문서의 개별 항목
- Mapping = 필드 타입 정의

**Kibana**
- Elasticsearch 데이터 조회 및 시각화

---

### 10. 원리로 이해할 것

1. Filebeat는 파일에서 새로운 로그를 읽고 전송한다.
2. Registry를 사용해 수집 상태를 관리한다.
3. Logstash는 Input → Filter → Output으로 데이터를 처리한다.
4. Elasticsearch는 로그를 색인하고 저장해 검색 가능하게 만든다.
5. Kibana는 Elasticsearch에 검색을 요청해 결과를 보여준다.
6. 로그가 보이지 않을 때는 전체 처리 흐름에서 실패 지점을 찾는다.

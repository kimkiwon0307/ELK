
# ELK 프로젝트 학습

## 1장 1교시. ELK 개념 및 중앙집중식 로그 관리

### 1. 로그(Log)란?

로그는 서버나 애플리케이션에서 발생한 사건을 기록한 데이터이다.

**로그 레벨**

| 레벨 | 의미 |
|---|---|
| DEBUG | 상세 디버깅 정보 |
| INFO | 정상적인 동작 기록 |
| WARN | 잠재적인 문제 및 경고 |
| ERROR | 오류 발생 |

**로그가 필요한 이유**
- 서버 및 애플리케이션 동작 확인
- 장애 발생 시 원인 추적
- 사용자 요청 및 오류 분석
- 시스템 운영 상태 점검

---

### 2. ELK의 등장 배경과 필요성

기존에는 서버에 직접 접속하여 로그를 확인했다.

서버가 여러 대로 증가하면 다음과 같은 문제가 발생한다.

- 각 서버에 개별적으로 접속해야 한다.
- 로그가 여러 서버에 분산되어 있다.
- 서버 간 요청 흐름을 추적하기 어렵다.
- 통합 검색 및 장애 분석에 시간이 오래 걸린다.

**해결 방법: 중앙집중식 로그 관리**

여러 서버에서 발생한 로그를 한곳에 모아 통합 검색하고 분석하는 방식이다.

**핵심:** 로그의 양뿐 아니라 로그가 여러 서버에 분산되어 있다는 점이 중요한 문제이다.

---

### 3. ELK 구성요소

| 기술 | 주요 역할 |
|---|---|
| Filebeat | 로그 파일 수집 및 전송 |
| Logstash | 로그 수신·가공·전달 |
| Elasticsearch | 로그 색인·저장·검색 |
| Kibana | 로그 조회 및 시각화 |

**ELK = Elasticsearch + Logstash + Kibana**

Filebeat는 로그 수집에 사용되는 별도의 도구이다.

---

### 4. 로그 처리 동작 원리

```text
Spring Boot
    ↓ 로그 생성
Filebeat
    ↓ 로그 수집 및 전송
Logstash
    ↓ 로그 가공
Elasticsearch
    ↓ 색인 및 저장
Kibana
    ↓ 조회 및 시각화
운영 엔지니어
```

정확한 데이터 흐름:

- 로그 수집·저장: Spring Boot → Filebeat → Logstash → Elasticsearch
- 로그 검색: Kibana → Elasticsearch → Kibana

Kibana는 Elasticsearch에 검색 요청을 보내 결과를 받아 표시한다.

---

### 5. ELK 기술 선택 이유와 대안

**ELK를 사용하는 이유**
- 여러 서버의 로그를 통합 관리
- 오류 로그 검색 및 분석
- 로그 데이터 가공
- 시간별 오류 발생 추이 시각화
- 장애 원인 분석 효율 향상

**반드시 모든 구성요소가 필요한 것은 아니다.**

예를 들어 다음과 같은 구성도 가능하다.

```text
Filebeat → Elasticsearch → Kibana
```

Logstash를 사용하지 않아도 로그를 수집하고 검색할 수 있다.

Logstash는 복잡한 로그 파싱과 가공이 필요할 때 유용하다.

Elastic Agent를 이용한 로그 수집도 대안이 될 수 있다.

**기술 선택 원칙**

기술은 많이 사용하는 것이 중요한 게 아니라 도입 목적과 필요성이 명확해야 한다.

---

### 6. 리눅스 로그 검색 명령어

```bash
# 로그 파일 전체 확인
cat app.log

# ERROR 로그 검색
grep "ERROR" app.log

# ERROR 로그가 포함된 줄 개수 확인
grep -c "ERROR" app.log

# 특정 요청 ID 검색
grep "req-003" app.log

# 마지막 3줄 확인
tail -n 3 app.log
```

**핵심**
- cat = 전체 내용 확인
- grep = 특정 문자열 검색
- grep -c = 일치하는 줄 개수 확인
- tail = 파일 마지막 부분 확인

요청 ID(requestId)는 동일한 요청에서 발생한 로그를 연결하여 분석하는 데 활용할 수 있다.

---

### 7. 장애 발생 시 기본 점검

로그가 검색되지 않는다면 다음 항목을 확인한다.

1. 애플리케이션에서 로그가 생성되었는가?
2. 예상한 경로에 로그 파일이 존재하는가?
3. 로그 파일을 읽을 권한이 있는가?
4. 검색 조건과 시간 범위가 올바른가?
5. 중앙 로그 수집 시스템에 정상 전달되었는가?

**장애 대응 원칙**

로그가 보이지 않는다고 ELK 장애라고 단정하지 않는다.

로그 생성부터 수집·저장·검색까지 단계별로 원인을 확인한다.

---

### 8. 확인문제 및 정답

**Q1. 로그의 주요 목적은?**

정답: 서버와 애플리케이션에서 발생한 사건을 기록한다.

**Q2. 중앙집중식 로그 관리가 필요한 이유는?**

정답: 여러 서버에 분산된 로그를 한곳에서 검색하고 분석하기 위해서이다.

**Q3. Filebeat의 역할은?**

정답: 로그 파일 수집 및 전송

**Q4. Logstash와 Elasticsearch의 차이는?**

정답:
- Logstash: 로그 수신·가공·전달
- Elasticsearch: 로그 색인·저장·검색

**Q5. Kibana의 역할은?**

정답: Elasticsearch의 데이터를 조회하고 시각화한다.

**Q6. 서버가 여러 대일 때 중앙집중식 로그 관리가 필요한 이유는?**

정답: 서버가 증가하면 로그가 각 서버에 분산되고 개별적으로 확인하기 어려워진다. 중앙집중식 로그 관리 시스템을 사용하면 여러 서버의 로그를 한곳에서 통합 검색하고 분석할 수 있다.

**Q7. Spring Boot에서 ERROR 로그가 발생하면 ELK는 어떻게 처리하는가?**

정답:
1. Spring Boot: 로그 생성
2. Filebeat: 로그 수집 및 전송
3. Logstash: 로그 수신 및 가공
4. Elasticsearch: 로그 색인·저장·검색
5. Kibana: 로그 조회 및 시각화

---

### 9. 반드시 암기할 것

- 로그 = 시스템에서 발생한 사건 기록
- 중앙집중식 로그 관리 = 여러 서버의 로그 통합 관리
- Filebeat = 수집
- Logstash = 가공
- Elasticsearch = 색인·저장·검색
- Kibana = 조회·시각화

### 10. 원리로 이해할 것

1. 서버가 증가하면 로그가 여러 서버에 분산된다.
2. 분산된 로그를 개별적으로 확인하면 장애 분석이 어려워진다.
3. 로그를 중앙에 수집하면 통합 검색과 분석이 가능해진다.
4. Filebeat, Logstash, Elasticsearch, Kibana는 서로 다른 역할을 담당한다.
5. 모든 환경에 ELK 전체 구성이 필요한 것은 아니다.

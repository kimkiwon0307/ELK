
# ELK 프로젝트 학습

## 1장. ELK 기초 이해 및 프로젝트 설계

### 1교시. ELK 개념 및 구성요소

### 1. 로그(Log)란?

로그는 서버나 애플리케이션에서 발생한 사건을 기록한 데이터이다.

**로그 레벨**
- DEBUG: 상세 디버깅 정보
- INFO: 정상적인 동작 기록
- WARN: 잠재적인 문제나 경고
- ERROR: 오류 발생

**로그가 필요한 이유**
- 서버 및 애플리케이션 동작 확인
- 장애 발생 시 원인 추적
- 사용자 요청 및 오류 분석
- 시스템 운영 상태 점검

### 2. 중앙집중식 로그 관리가 필요한 이유

기존 방식은 서버에 직접 접속해 로그를 확인한다.

서버가 많아지면 다음과 같은 문제가 발생한다.

- 서버마다 접속해서 로그를 확인해야 한다.
- 여러 서버에 걸친 요청을 추적하기 어렵다.
- 로그 검색과 분석에 시간이 오래 걸린다.
- 서버 장애 시 로그가 유실될 수 있다.

**해결 방법:** 여러 서버의 로그를 중앙으로 수집하고 저장하여 통합 검색 및 분석한다.

### 3. ELK 구성요소

| 구성요소 | 역할 |
|---|---|
| Elasticsearch | 데이터 저장, 검색 및 분석 |
| Logstash | 데이터 수집, 가공 및 전달 |
| Kibana | 데이터 검색 및 시각화 |
| Filebeat | 로그 파일 수집 및 전송 |

ELK는 Elasticsearch, Logstash, Kibana의 약자이다.

Filebeat는 로그 수집을 담당하는 도구이며, Elastic Stack 구성에 활용된다.

### 4. 로그 처리 흐름

```text
Spring Boot
    ↓ 로그 생성
Filebeat
    ↓ 로그 수집 및 전송
Logstash
    ↓ 로그 파싱 및 가공
Elasticsearch
    ↓ 로그 저장 및 검색
Kibana
    ↓
운영자가 로그 조회 및 장애 분석
```

※ Filebeat는 Logstash를 거치지 않고 Elasticsearch로 직접 전송할 수도 있다.

### 5. 리눅스 로그 확인 명령어

```bash
# 로그 파일 전체 확인
cat app.log

# 마지막 10줄 확인
tail -n 10 app.log

# 실시간 로그 확인
tail -f app.log

# ERROR 로그 검색
grep "ERROR" app.log

# ERROR가 포함된 줄 개수 확인
grep -c "ERROR" app.log
```

### 6. ELK 도입 목적

- 여러 서버의 로그를 한곳에서 관리
- 장애 발생 시 빠른 로그 검색
- 오류 발생 추이 시각화
- 사용자 요청 흐름 추적
- 로그 기반 장애 분석 및 운영 효율 향상

### 7. 확인문제 및 정답

**Q1. 로그의 주요 목적은?**

정답: 서버와 애플리케이션에서 발생한 사건을 기록한다.

**Q2. Elasticsearch의 주요 역할은?**

정답: 데이터 저장, 검색 및 분석

**Q3. Logstash의 주요 역할은?**

정답: 데이터 수집, 가공 및 전달

**Q4. Kibana의 주요 역할은?**

정답: 저장된 데이터 검색 및 시각화

**Q5. Filebeat의 역할은?**

정답: 로그 파일을 수집하여 Logstash 또는 Elasticsearch로 전달한다.

**Q6. 서버가 여러 대일 때 중앙집중식 로그 관리가 필요한 이유는?**

정답: 서버가 증가하면 개별 서버에 접속해 로그를 확인하는 데 많은 시간이 소요되고, 여러 서버에 걸친 요청을 추적하기 어렵다. 중앙집중식 로그 관리를 도입하면 로그를 한곳에 모아 효율적으로 검색하고 분석할 수 있다.

---

### 8. 핵심 요약

- Filebeat = 로그 수집
- Logstash = 로그 가공
- Elasticsearch = 로그 저장 및 검색
- Kibana = 로그 시각화
- ELK 도입 목적 = 중앙집중식 로그 관리 및 장애 분석

**학습 결과:** ELK 구성요소의 역할과 중앙집중식 로그 관리의 필요성을 이해했다.

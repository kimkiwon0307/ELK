
# ELK 프로젝트 학습

## 1장 3교시. ELK 프로젝트 아키텍처 설계

### 1. 아키텍처란?

아키텍처는 시스템의 구성요소를 어떻게 배치하고 연결할지 결정하는 설계 구조이다.

설계 시 고려할 사항:
- 서버 수와 역할
- CPU, 메모리, 디스크 자원
- 네트워크 연결 및 포트
- 로그 수집 및 저장 방식
- 보안 및 장애 대응

---

### 2. ELK 프로젝트 아키텍처

이번 프로젝트는 Ubuntu VM 2대를 사용한다.

```text
[VMware Workstation]
        |
        | NAT Network
        |
+-----------------------------+
| VM1 - APP Server            |
|                             |
| Spring Boot                 |
|     | 로그 생성             |
|     v                       |
| Filebeat                    |
|     | 로그 수집 및 전송     |
+-----|-----------------------+
      |
      | TCP 5044
      v
+-----------------------------+
| VM2 - ELK Server            |
|                             |
| Logstash                    |
|     | 로그 가공             |
|     v                       |
| Elasticsearch               |
|     | 로그 색인 및 저장     |
|     ^ 검색 요청 / 응답      |
|     v                       |
| Kibana                      |
+-----------------------------+
      ^
      | TCP 5601
      |
 Windows 웹 브라우저
```

**VM1 구성**
- Spring Boot: 애플리케이션 실행 및 로그 생성
- Filebeat: 로그 파일 수집 및 전송

**VM2 구성**
- Logstash: 로그 수신 및 가공
- Elasticsearch: 로그 색인·저장·검색
- Kibana: 로그 조회 및 시각화

### 3. VM을 분리하는 이유

1. 애플리케이션과 로그 관리 시스템의 자원 사용을 분리한다.
2. 장애 발생 시 어느 서버에 문제가 있는지 파악하기 쉽다.
3. 서버 간 로그 전송 및 네트워크 장애를 실습할 수 있다.
4. 서버별 역할을 구분해 운영할 수 있다.

단, 두 VM이 하나의 물리 PC에서 실행되므로 물리 장비 장애까지 격리되는 것은 아니다.

---

### 4. VM 권장 사양

| 항목 | VM1 (APP) | VM2 (ELK) |
|---|---|---|
| OS | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |
| vCPU | 2 | 4 |
| RAM | 4GB | 12GB |
| Disk | 40GB | 100GB |
| 주요 서비스 | Spring Boot, Filebeat | Elasticsearch, Logstash, Kibana |

위 사양은 개인 실습을 위한 시작안이다.

**ELK 서버에 메모리가 더 필요한 이유**
- Elasticsearch: JVM 기반 색인 및 검색
- Logstash: JVM 기반 로그 처리
- Kibana: 웹 애플리케이션 실행
- Elasticsearch의 파일 캐시 사용

메모리가 부족하면 성능 저하나 서비스 실행 실패가 발생할 수 있다.

---

### 5. 네트워크 및 포트

| 포트 | 용도 |
|---|---|
| TCP 22 | SSH 원격 관리 |
| TCP 8080 | Spring Boot API |
| TCP 5044 | Filebeat → Logstash |
| TCP 9200 | Elasticsearch API |
| TCP 5601 | Kibana 웹 접속 |

**보안 원칙**
- 5044: APP 서버에서의 접근 허용
- 5601: 관리자 PC에서만 접근 허용
- 9200: Docker 내부 통신 중심으로 구성
- 22: 관리자 접근 제한
- 외부에 불필요한 포트 개방 금지

---

### 6. 설치 및 운영 방식

| 구성요소 | 설치 방식 |
|---|---|
| Spring Boot | Java 애플리케이션 |
| Filebeat | Ubuntu 직접 설치 |
| Elasticsearch | Docker |
| Logstash | Docker |
| Kibana | Docker |
| ELK 통합 관리 | Docker Compose |

**Docker Compose 선택 이유**

여러 컨테이너를 하나의 설정 파일로 정의하고 통합 관리할 수 있기 때문이다.

```bash
docker compose up -d
```

- up: 서비스 생성 및 시작
- -d: 백그라운드 실행

Elasticsearch 데이터는 Docker Volume을 사용해 컨테이너 재생성 시에도 유지하도록 설계한다.

---

### 7. 로그 수집 대상

Spring Boot 테스트 API를 이용해 로그를 생성한다.

| API | 목적 |
|---|---|
| /health | 정상 동작 확인 |
| /test/error | HTTP 500 오류 발생 |
| /test/slow | 응답 지연 발생 |
| /test/db | DB 연결 상태 확인 |

수집할 주요 로그 필드:

- @timestamp: 이벤트 발생 시간
- level: 로그 레벨
- requestId: 요청 식별자
- method: HTTP 메서드
- path: 요청 경로
- status: HTTP 상태 코드

---

### 8. 시스템 정상 동작 검증

다음 흐름을 확인해야 한다.

1. Spring Boot에서 테스트 로그 생성
2. 로그 파일 기록 확인
3. Filebeat 수집 및 전송 확인
4. Logstash 수신 및 가공 확인
5. Elasticsearch 문서 저장 확인
6. Kibana 로그 검색 확인

**핵심:** 컨테이너가 실행 중인 것만으로 정상이라고 판단하지 않는다. 실제 로그가 생성되어 Kibana에서 검색되는지 검증한다.

---

### 9. 장애 발생 시 점검 순서

Kibana에서 ERROR 로그가 검색되지 않는 상황을 가정한다.

| 순서 | 구성요소 | 점검 내용 |
|---|---|---|
| 1 | Spring Boot | 로그 파일이 생성되었는가? |
| 2 | Filebeat | 로그를 읽고 전송하는가? |
| 3 | Logstash | 로그를 수신하고 가공하는가? |
| 4 | Elasticsearch | 로그가 저장되고 검색되는가? |
| 5 | Kibana | Data View, 시간 범위, 검색 조건이 정상인가? |

**중요**

Elasticsearch에 데이터가 정상 저장되어 있는데 Kibana에서 보이지 않는다면 우선 다음을 확인한다.

- Data View 설정
- 조회 시간 범위
- 검색 필터
- 접근 권한

### 10. 확인문제 및 정답

**Q1. VM을 2대로 분리하는 이유는?**

정답: 애플리케이션과 ELK의 자원을 분리하고 장애 원인을 파악하기 쉽게 하기 위해서이다.

**Q2. Filebeat는 어느 서버에 설치하는가?**

정답: VM1(APP 서버)

**Q3. Filebeat에서 Logstash로 로그를 전송할 때 사용하는 포트는?**

정답: TCP 5044 (이번 프로젝트 설정 기준)

**Q4. ELK 서버에 메모리를 더 많이 할당하는 이유는?**

정답: Elasticsearch, Logstash, Kibana가 함께 메모리를 사용하기 때문이다.

**Q5. ELK가 정상 동작하는지 검증하는 방법은?**

정답: 테스트 로그를 발생시킨 뒤 Kibana에서 실제 로그가 검색되는지 확인한다.

**Q6. VM1과 VM2의 구성 및 분리 이유는?**

정답:
- VM1: Spring Boot + Filebeat
- VM2: Logstash + Elasticsearch + Kibana
- 분리 이유: 자원 관리, 역할 분리 및 장애 원인 분석

**Q7. Kibana에서 ERROR 로그가 보이지 않는다면?**

정답:
1. Spring Boot 로그 생성 확인
2. Filebeat 수집 및 전송 확인
3. Logstash 수신 및 처리 확인
4. Elasticsearch 저장 및 검색 확인
5. Kibana Data View와 조회 설정 확인

---

### 11. 핵심 암기

- VM1 = Spring Boot + Filebeat
- VM2 = Logstash + Elasticsearch + Kibana
- 5044 = 로그 전송
- 9200 = Elasticsearch API
- 5601 = Kibana 웹 접속
- 서버 분리 이유 = 자원 분리 + 장애 분석
- 정상 검증 = 실제 로그 생성부터 Kibana 검색까지 확인
- 장애 대응 = 로그 전달 경로에 따라 원인 좁히기

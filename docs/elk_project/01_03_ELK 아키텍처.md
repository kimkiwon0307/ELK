
# ELK 프로젝트 학습

## 1장 3교시. ELK 아키텍처 설계 및 실습 환경 준비

### 1. 아키텍처란?

아키텍처(Architecture)는 시스템을 구성하는 요소와 각 요소가 연결되는 구조이다.

**아키텍처를 설계하는 이유**
- 서버별 역할 결정
- CPU·메모리·디스크 자원 계획
- 네트워크와 포트 구성
- 기술 선택과 보안 정책 결정
- 장애 발생 시 영향 범위 및 점검 대상 파악

**핵심:** 서버를 설치하는 방법뿐 아니라 왜 그렇게 구성하는지 설명할 수 있어야 한다.

---

### 2. ELK 프로젝트 전체 아키텍처

**실습 환경**
- VMware Workstation
- Ubuntu Server 24.04 LTS
- VMware NAT 네트워크
- VM 2대

**VM1: APP01**
- Spring Boot: 애플리케이션 실행 및 로그 생성
- Filebeat: 로그 파일 수집 및 전송

**VM2: ELK01**
- Logstash: 로그 수신·가공·전달
- Elasticsearch: 로그 색인·저장·검색
- Kibana: 로그 조회·시각화

**로그 저장 흐름**

Spring Boot → Filebeat → Logstash → Elasticsearch

**로그 검색 흐름**

Kibana → Elasticsearch → Kibana

**서버를 분리하는 이유**
1. 애플리케이션과 로그 분석 시스템의 역할 분리
2. CPU·메모리 등 자원 사용 분리
3. 장애 발생 시 원인 구분 용이
4. 서로 다른 서버 간 로그 전송 실습

주의: 서버가 2대라고 자동으로 고가용성(HA)이 구현되는 것은 아니다.

---

### 3. 서버 권장 사양

| 항목 | APP01 | ELK01 |
|---|---|---|
| OS | Ubuntu 24.04 | Ubuntu 24.04 |
| CPU | 2 vCPU | 4 vCPU |
| RAM | 4GB | 12GB |
| Disk | 40GB | 100GB |
| 주요 프로그램 | Spring Boot, Filebeat | Logstash, Elasticsearch, Kibana |

위 사양은 이번 학습 프로젝트의 권장 구성이다.

**ELK01에 메모리를 더 많이 할당하는 이유**

Elasticsearch는 JVM Heap과 파일 시스템 캐시 등을 활용하며, 로그 색인과 검색 시 메모리가 중요하다.

Logstash와 Kibana도 별도로 메모리를 사용하므로 ELK01에 더 많은 자원을 배정한다.

**기본 개념**
- CPU: 명령과 작업 처리
- RAM: 실행 중인 데이터 및 작업 처리
- Disk: 로그와 인덱스 데이터 보관

---

### 4. 네트워크 및 주요 포트

**IP와 포트의 차이**
- IP: 통신할 서버의 주소
- Port: 서버에서 통신할 프로그램의 접속 지점

**주요 포트**

| 포트 | 서비스 | 용도 |
|---|---|---|
| 22/TCP | SSH | 원격 서버 관리 |
| 8080/TCP | Spring Boot | 애플리케이션 접속 |
| 5044/TCP | Logstash | Filebeat 로그 수신 |
| 9200/TCP | Elasticsearch | REST API |
| 5601/TCP | Kibana | 웹 UI |

**반드시 기억**
- 5044 = Logstash
- 9200 = Elasticsearch
- 5601 = Kibana

5044는 이번 프로젝트에서 설정할 Logstash 수신 포트이며 변경 가능하다.

**보안 설계**
- SSH는 관리자에게만 접근 허용
- 5044는 APP01에서 ELK01로의 접근 허용
- Elasticsearch 9200은 외부 인터넷에 공개하지 않음
- Kibana 5601은 허용된 관리자만 접근
- 실제 운영에서는 TLS·인증·권한 및 방화벽도 고려

### 5. Docker Compose를 선택한 이유

**Docker**
애플리케이션과 실행 환경을 컨테이너 단위로 실행하고 관리하는 기술.

**Docker Compose**
여러 컨테이너의 실행 설정을 하나의 YAML 파일에서 정의하고 관리하는 도구.

이번 프로젝트에서는 Elasticsearch, Logstash, Kibana를 Docker Compose로 관리한다.

**대표 명령어**

```bash
docker compose up -d
docker compose ps
docker compose logs
docker compose down
```

| 명령어 | 의미 |
|---|---|
| up -d | 컨테이너 생성·백그라운드 실행 |
| ps | 컨테이너 상태 확인 |
| logs | 컨테이너 로그 확인 |
| down | 컨테이너 및 Compose 네트워크 등 중지·제거 |

주의:
docker compose down -v는 데이터 볼륨까지 삭제할 수 있으므로 주의한다.

**Docker Compose 선택 이유**
1. 여러 서비스의 설정을 한 파일에서 관리
2. 실행 환경을 재구축하기 편리
3. 이미지·네트워크·볼륨 등을 명확히 정의
4. GitHub에서 설정을 버전 관리하기 편리

**대안**
Ubuntu에 Elasticsearch, Logstash, Kibana를 각각 직접 설치할 수도 있다.

### 6. Ubuntu 서버 환경 확인

APP01과 ELK01에서 실행한다.

```bash
# 운영체제 확인
cat /etc/os-release

# CPU 확인
lscpu

# 메모리 확인
free -h

# 디스크 확인
lsblk
df -h /

# IP 주소 확인
ip -br address

# 라우팅 테이블 확인
ip route
```

**명령어 의미**

| 명령어 | 역할 |
|---|---|
| lscpu | CPU 정보 확인 |
| free -h | 메모리 용량 및 사용량 확인 |
| lsblk | 디스크·파티션 확인 |
| df -h / | 루트 파일시스템 용량 확인 |
| ip -br address | 네트워크 인터페이스·IP 확인 |
| ip route | 라우팅 정보 확인 |

**검증 기준**
- OS 버전이 올바른가?
- CPU·메모리가 계획한 사양과 일치하는가?
- 디스크 용량이 충분한가?
- 두 VM에 IP가 할당되었는가?
- 기본 게이트웨이가 설정되었는가?

### 7. 서버 간 네트워크 연결 확인

```bash
# 현재 서버 IP 확인
hostname -I

# 다른 서버로 Ping 테스트
ping -c 3 ELK01_IP
```

ELK01_IP는 실제 IP로 변경한다.

**핵심 원리**

Ping 성공은 ICMP 통신 확인이지, TCP 5044 포트 연결 성공을 의미하지 않는다.

따라서 실제 구축 후에는 다음 항목도 확인해야 한다.

1. Logstash 실행 상태
2. TCP 5044 리스닝 상태
3. Filebeat의 목적지 IP·포트
4. 방화벽 허용 여부

### 8. Elasticsearch 커널 설정

**vm.max_map_count란?**

Linux 프로세스에서 사용할 수 있는 메모리 매핑 영역 수의 제한을 설정하는 커널 파라미터이다.

Elasticsearch는 메모리 매핑을 사용하므로 이 설정을 확인해야 한다.

**현재 값 확인**

```bash
sysctl vm.max_map_count
```

값이 1048576보다 작다면 ELK01에서 설정 파일을 작성한다.

```bash
sudo nano /etc/sysctl.d/99-elasticsearch.conf
```

파일 내용:

```ini
vm.max_map_count=1048576
```

적용 및 검증:

```bash
sudo sysctl --system
sysctl vm.max_map_count
```

**예상 결과**

```text
vm.max_map_count = 1048576
```

이미 1048576 이상이라면 수정하지 않아도 된다.

**핵심 원리**

운영체제의 메모리 매핑 수 제한이 부족하면 Elasticsearch 실행에 문제가 발생할 수 있다.

### 9. 장애 대응 기본 원칙

| 장애 상황 | 주요 점검 대상 |
|---|---|
| ELK01이 느림 | CPU·RAM·디스크 자원 |
| APP01에서 ELK01로 통신 실패 | IP·라우팅·방화벽 |
| Logstash 연결 실패 | 5044 포트·서비스 상태 |
| Elasticsearch 시작 실패 | 커널 설정·메모리·권한·로그 |
| Kibana 접속 실패 | 실행 상태·5601 포트·접근 설정 |

**장애 예시**

상황:
APP01에서 ELK01로 Ping은 성공하지만 Filebeat가 Logstash에 연결하지 못한다.

점검 순서:
1. Logstash가 실행 중인지 확인한다.
2. Logstash가 5044 포트에서 대기 중인지 확인한다.
3. Filebeat에 설정한 IP·포트가 올바른지 확인한다.
4. 방화벽에서 TCP 5044가 허용되어 있는지 확인한다.
5. TLS 설정 등 연결 관련 오류를 확인한다.

**중요**

서비스가 동작하지 않는다고 바로 재설치하지 않는다.

서버 상태 → 네트워크 → 포트 → 서비스 설정 → 애플리케이션 로그 순서로 원인을 좁혀 간다.

### 11. 반드시 암기할 것

**서버 역할**
- APP01: Spring Boot + Filebeat
- ELK01: Logstash + Elasticsearch + Kibana

**포트**
- 5044: Logstash
- 9200: Elasticsearch
- 5601: Kibana

**명령어 목적**
- free: 메모리 확인
- df: 파일시스템 용량 확인
- ip: 네트워크 확인
- ping: ICMP 연결 확인
- docker compose: 여러 컨테이너 관리
- sysctl: 커널 파라미터 확인·설정

### 12. 원리로 이해할 것

1. 아키텍처는 서버 역할·자원·네트워크를 고려하여 설계한다.
2. APP과 ELK 서버를 분리해 역할과 자원을 구분한다.
3. 서버의 IP와 서비스 포트는 서로 다른 개념이다.
4. Ping 성공만으로 특정 서비스의 TCP 연결을 보장하지 않는다.
5. Docker Compose로 여러 컨테이너를 통합 관리한다.
6. Elasticsearch는 자원과 커널 설정을 고려해야 한다.
7. 장애 발생 시 무조건 재설치하지 않고 원인을 단계적으로 확인한다.
